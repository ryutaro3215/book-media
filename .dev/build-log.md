## T25: 記事投稿用のローカルWebアプリ（段階1）— 2026-08-06

### 作ったもの

| ファイル | 役割 |
|---|---|
| `src/pages/admin.astro` | 入力画面。`npm run dev` → `/admin` |
| `scripts/lib/admin-dev-server.mjs` | 裏側の口（ISBN取得・ファイル書き出し）。**dev サーバーにだけ生える** |
| `scripts/lib/article-file.mjs` | frontmatter の組み立て。**CLI と画面の共通処理** |
| `scripts/strip-admin.mjs` | ビルド後に `dist/` から `/admin` を消す |

### 詰まった点と判断

**Astro の API ルートが使えなかった。**
`src/pages/api/isbn.json.ts` に置いた handler は、開発サーバーでも
`?isbn=…` が届かなかった。`url` からも `request.url` からも読めない。
POST のボディに変えても `request.json()` が落ちる。

原因は `output: "static"` でこのルートが**事前生成の対象**になること。
静的出力では実リクエストとして扱われない。`export const prerender = false`
にすればよいが、**アダプタが必要になり本番構成（Cloudflare Pages・静的）が変わる**。
記事を書くための道具のために本番の出し方を変えるのは順序が逆なので採らなかった。

**Vite プラグイン（`apply: "serve"`）に移した。**
結果として当初の懸念（本番ビルドに混入しないか）が、
実行時チェックではなく**そもそもビルドで読み込まれない**という形で解けた。
`astro.config.mjs` の `vite.plugins` に足すだけで済む。

### 本番に出さないための3層

1. 裏側の口は Vite の `apply: "serve"` プラグイン → **ビルドに存在しない**
2. `scripts/strip-admin.mjs` が `dist/` から `/admin` を消す
   （消せなかったらビルドを失敗させる）
3. `admin.astro` 自身が `import.meta.env.DEV` を見て中身を描画しない

### 見落としていて直した点

**sitemap に `/admin/` が載っていた。**
`@astrojs/sitemap` は `strip-admin.mjs` より先に走るので、
ファイルを消しても sitemap は申告し続ける。
Search Console に404が出るところだった。`astro.config.mjs` の filter に追加。

### 段階2・3をやらなかった理由

本文（Markdown）編集とプレビューは作っていない。
**長文は結局エディタが一番速く、書き直しはもっと速い。**
いま実際に困っていたのは「919件から選ぶ」「打ち間違えたら最初からやり直し」の2つで、
どちらも frontmatter の入力を画面にするだけで解ける。
運用してみて足りなければ足す。

## T26: /admin で長文も書けるようにする（段階2）— 2026-08-06

### 作ったもの

| ファイル | 役割 |
|---|---|
| `scripts/lib/article-file.mjs` | `readArticle` / `listArticles` / `isStale` を追加。`buildArticle` が本文・`draft`・`updatedAt`・長文を受け取れるようにした |
| `scripts/lib/admin-dev-server.mjs` | `/api/articles.json` と `/api/article.json` を追加。保存に編集モードを足した |
| `src/pages/admin.astro` | 記事の一覧・読み込み、長文4種の入力欄と文字数表示 |

段階1で「長文は結局エディタが速い」と判断して見送った部分を、
運用の方針が「**書くのは /admin に寄せる**」に決まったので作った。

### 詰まった点と判断

**段階1は「生成」で、段階2は「編集」だった。**
`buildArticle` は新規ファイルを作る関数で、既存ファイルを読む手段が無かった。
frontmatter と本文を分けて読む `readArticle` を足すまで、
保存のたびに本文が消える。ここが最悪の事故なので先に作った。

**公開済みの記事を開いて保存すると、下書きに戻る。**
`draft` は `buildArticle` の既定が `true`。編集で送り返さないと、
公開中の記事が `draft: true` になってサイトから消える。
`draft` / `publishedAt` を読み込み時に抱えて、保存時にそのまま返す形にした。

**長文の空欄は「送らない」。**
空文字を送ると `buildArticle` の `TODO:` の枠が消え、
`draft: false` にしたときに `reason` が `min(1)` で落ちる。
未入力は `undefined` にして、枠はサーバー側に入れさせている。
**`whyBuried` だけは事情が違い**、値が無いと項目ごと出力されないので、
印だけ付いて未記入のときは `TODO:` の文字列を明示的に送る。
そうしないと「知る人ぞ知る本」の印そのものが消える。

**文字数は目安であって制約にしない。**
300〜600字といった数字は書く前の見当で、外れたら弾く筋のものではない。
範囲外は色を変えるだけにした。**書く手を止めないことを優先している。**

**衝突対策は最小限だけ入れた。**
「エディタと /admin を同時に触らない」と運用で決めたので、本来は不要。
ただし**ビルドが落ちてエディタで直したとき**と **`git pull` したとき**は
運用では防げない。読み込み時の `mtimeMs` を持って、
ずれていたら保存前に確認するだけにした。数行で済み、失うのが原稿そのものなので割に合う。

### 見落としていて直した点

**連続で保存すると毎回「外で変わっています」と出た。**
保存自体が mtime を変えるため。保存の応答で新しい `mtimeMs` を返し、
画面側で持ち直すようにした。

**開いた本文に雛形コメントが残り、毎回手で消すことになった。**
`<!-- 導入文をここに書く… -->` は未記入の目印であって原稿ではないので、
読み込み時に空欄として扱う。**「要確認」コメントはそのまま残す** —
あれは人が現物と照らして消すものなので、勝手に落とすと確認が抜ける。

**小トピックが空のまま読み込まれた。**
候補は大トピックの `change` で作られるので、
`#topic` に値を入れただけでは `option` が無く、`#subtopic` への代入が落ちる。
読み込み時に `change` を明示的に発火させてから小トピックを入れている。

**削除機能は作らなかった。**
消すのはファイルを消せば済む。画面から消せると、
誤操作で失うのが書き上げた原稿になる。

## T27: /admin で書影を確かめて置けるようにする — 2026-08-06

### 作ったもの

| ファイル | 役割 |
|---|---|
| `src/lib/cover.ts` | `LOCAL_EXTENSIONS` を公開した（許可する拡張子の出どころを1つにする） |
| `scripts/lib/admin-dev-server.mjs` | `/api/isbn.json` が書影を返すようにし、`/api/upload-cover.json` を追加 |
| `src/pages/admin.astro` | 1冊ごとの書影欄（サムネイル・取得元・アップロード・許諾の警告） |

### 詰まった点と判断

**書影の解決を書き写さなかった。**
このプラグインは `.mjs` で、`cover.ts` は TypeScript。素直には読めない。
だが解決順を2箇所に持つと、**画面が「取れない」と言うので画像を置いたのに、
ビルドでは openBD から取れていた**（あるいはその逆）が起こりうる。
画面を見ても気づけない食い違いなので、`article-file.mjs` を CLI と共有したときと
同じ判断をした。手段は dev サーバーの `ssrLoadModule("/src/lib/cover.ts")`。
**この口は dev にしか生えない**ので、TypeScript の変換器は常に手元にある。
失ったのは、`resolveCover` のプロセス内メモ化が Astro 側とは別インスタンスになること
（外部APIを1ISBNにつき最大2回引く）。**自前画像の判定はメモ化の外**なので、
「置いたのに反映されない」は起きない。

**自前画像がキャッシュより先に来ることを実際に確かめた。**
`.cache/covers.json` に openBD のURLが載っている `9784130420655` に画像を置き、
次の解決が `local` になることを見た。`resolveCover` が
`findLocalCover` をメモ化とディスクキャッシュの手前で見ているため。
**アップロード後にキャッシュを消す処理は要らない。**

**拡張子違いの残留が、いちばん分かりにくい事故だった。**
`.jpg` があるところに `.png` を置くと両方が残り、`LOCAL_EXTENSIONS` の順で `.jpg` が勝つ。
アップロードは成功し、ファイルもできているのに書影が変わらない。
確認のうえで**1ISBN 1ファイルに揃える**（古い方を消す）ことにした。
どちらを残すか選ばせる案もあったが、選ばせるほどの判断ではなく、
選択肢を出すこと自体が「両方残せる」と誤解させる。

**拡張子は自己申告なので信じない。**
ローカル専用の口だが、`.jpg` にリネームしたテキストを置くと
**壊れた書影がそのまま本番に出る**。表示が壊れてから原因をたどるのは高くつくので、
先頭バイト（JPEG の `FF D8 FF`・PNG のシグネチャ・`RIFF`+`WEBP`）で実体を確かめ、
拡張子と食い違えば弾く。上限は 5MB（書影は大きくても数百KB）。

**許諾はチェックボックスにしなかった。**
画面には許諾の有無を判定する手段が無く、止めても押すだけの儀式になる。
代わりに**何が起きるのか**を書いた —「自サイトから配信される」「複製・公衆送信にあたる」
「出版社の許諾が要る」。読んで判断できる文にすることの方が、操作を止めるより効く。

**base64 で送る。** multipart にするとパーサをこのミドルウェアに抱えることになる。
置くのは1回1ファイル・数百KBで、3割増しを気にする場面ではない。
既存の口がすべて POST・JSON なので、形も揃う。

### 見落としていて直した点

**書誌が取れない本でも書影は取れることがある。**
最初は `found` のときだけ書影を描いていた。`lookupIsbn` と `resolveCover` は
別の問い合わせなので、片方の失敗でもう片方を落とさないよう並行にして、
書影の表示は `found` と無関係に更新する。

**置いた直後に画像が出ないことがある。**
`/covers/<ISBN>.jpg` はアップロード前に 404 を返しており、
ブラウザがそれを握っていると差し替わらない。`?t=<時刻>` を付けて読ませている。

**ブラウザのJSは curl では確かめられない。**
`renderCover` / `uploadCover` を最小の DOM もどきに載せて Node から実際の口へ投げ、
7経路（書影なし・新規・上書き・確認の中止・偽装ファイル・ISBN不正・openBD取得）の
表示と文言を確認した。

## T28: 書影を登録時に一度だけ引く — 2026-08-06

### きっかけ

ユーザーから「APIでの画像取得率がめちゃくちゃ低い」「以前まで正常に取得できていたものが
映らなくなってる」との指摘。**コードのバグではなく、2つの別々の原因が重なっていた。**

1. **Google Books の1日あたりの上限を使い切っていた**
   記事の一括生成（21本105冊 + 19本95冊、1冊あたり最大5回の照会）で、
   無料枠 1,000件/日を超過。実測で 51/51 が 429。
   `"Quota exceeded for quota metric 'Queries' and limit 'Queries per day'"`
2. **キャッシュが cwd 基準だった**
   確認のため dev サーバーをワークツリーから起動したところ、
   `.cache/covers.json` が別物（本体170件 / ワークツリー24件）になり、
   **前は映っていた本が映らなくなった**

### 直したこと

書影は本ごとに一度決まれば変わらない。**登録のときに一度だけ引いて、
結果をリポジトリに持つ**構造にした。

| | 変更前 | 変更後 |
|---|---|---|
| 記録の場所 | `.cache/covers.json`（git管理外・cwd依存） | `src/data/covers.json`（リポジトリ内） |
| ビルド時 | 外部APIを叩く | **記録を読むだけ** |
| 引くタイミング | 表示のたび | `/admin` の「取得」／`npm run sync:covers` |
| 書影なし | 記録しない（毎回引き直す） | **記録する** |
| 429・タイムアウト | `null` = 書影なしと同じ | **記録しない**（区別する） |

### 画像をダウンロードしなかった理由

ユーザーの当初案は「登録時に画像をダウンロードして `public/covers/` に保存」。
狙い（APIを叩くのは登録時だけ）は正しいが、**保存する対象が問題だった。**

`docs/covers.md` は「自サイト配信は複製・公衆送信にあたり、出版社の許諾が要る。
許諾が取れていない書影をこのディレクトリに置いてはならない」と定めている。
一括ダウンロードは**218冊ぶんこのルールを機械的に破る**ことになる。

**保存するのを画像ではなくURLにすれば、狙った効果はそのまま得られる**ため、
そちらを採った。失うのは「URLが腐りうる」ことだけで、これは運用でカバーできる。
法的な問題は運用でカバーできない。

### 実装で効いた判断

- **取得処理を `scripts/lib/cover-lookup.mjs` に集約した。**
  `sync-covers.mjs` と `/admin` の両方が使う。2箇所に分かれると
  「画面では取れるがコマンドでは取れない」が起きうる
  （CLI と `/admin` で `article-file.mjs` を共有したのと同じ理由）
- `/admin` は記録に書いたあと、**`cover.ts` に解決させ直して**画面に出す。
  画面の答えとビルドの答えを必ず一致させるため

### 確認

上限超過の状態で `npm run sync:covers` を実行 →
**51件すべて「取得できず」となり、記録は170件のまま変わらなかった。**
以前はここで全部が「書影なし」として焼き付いていた。

## /admin の書誌取得が、既に整った値を図書館形式で上書きしていた — 2026-08-06

### 症状

`/admin` で「取得」を押すと、記事の書誌が劣化した。

```
author: "クレイトン・クリステンセン" → "Christensen,ClaytonM 玉田,俊平太 伊豆原,弓"
author: "神取 道宏"                → "神取,道宏"
title:  "とにかく仕組み化 : 人の上に…" → "とにかく仕組み化 = Anyway,Systematize : …"
```

### 原因

書影の不具合（T28）と**同じ構図**だった。

```js
title: g?.title || o?.title || "",
author: g?.author || o?.author || "",
```

書名・著者は Google Books を優先している（openBD は叢書名・巻次・図書館形式が混ざるため）。
ところが `fetchGoogleBooks` は 429 でも `null` を返していたので、
**上限に当たった日は「値が無い」と区別がつかず、静かに openBD の値へ落ちていた。**

### 直したこと

1. **取得結果を3状態にした** — `found` / `none` / `unavailable`。
   429・5xx・タイムアウトは `unavailable`
2. **優先する側が `unavailable` のとき、その項目は空で返す。**
   画面側は空を代入しないので、**既存の値がそのまま残る**。
   あわせて理由を警告に出す（「Google Books が応答しません…書名・著者は今回更新しません」）
3. **openBD の整形を実測に合わせた。**
   `／` 区切りしか想定していなかったが、実際には全角スペース区切り・`姓,名` 形式もある。
   並列書名（` = Anyway,Systematize`）も落とすようにした

### 確認

上限超過の状態で `/api/isbn.json` を叩き、
`title: ""` / `author: ""` / `publisher: "翔泳社"`（openBD は生きている）と、
`degraded: ["title","author"]` が返ることを確認した。

### 残っていること

**既に劣化した記事7本の値は、コードの修正では戻らない。**
上限がリセットされたあとに `/admin` で「取得」を押し直せば正しい値が入る。

## /admin が Google Books をキー無しで叩いていた — 2026-08-08

### 症状

ユーザーから「`/admin` で Google Books API を叩いてもエラーになる。
もう1日の上限はリセットされているはずなのに」。

### 原因

**`astro dev` は `.env` を `import.meta.env` にしか入れない。**
`process.env` には何も入らない。

`scripts/lib/admin-dev-server.mjs` は Vite プラグインとして Node 側で動くので
`process.env.GOOGLE_BOOKS_API_KEY` を見ていたが、そこは空だった。
**キー無しのリクエストは共有の枠を使うため、すぐ 429 が返る。**

実測:

```
キーあり  HTTP 200
キーなし  HTTP 429  "Quota exceeded ... for consumer 'project_number:624717413613'"
```

**consumer の project_number が違う。** 自分のプロジェクトの枠は余っていて、
匿名の共有枠を使い切っていただけだった。

`src/lib/cover.ts` では以前この罠を踏んでおり、`import.meta.env` を先に見て
`process.env` にフォールバックする形で回避してある。**プラグイン側には
その対策が入っていなかった。**

私が動作確認するときは毎回 `set -a; . ./.env; set +a` してから起動していたため、
**手元では再現しなかった。** ユーザーは `npm run dev` だけを叩く。

### 直したこと

1. プラグインの読み込み時に `loadEnv(".env")` を呼ぶ
2. **起動時にキーの有無を警告する。** 無いと書誌も書影も静かに劣化するため
3. **警告文で原因を分けた。** 「キーが渡っていない」と「自分の枠を使い切った」は
   どちらも 429 になるが直し方が違う。実際に、キー未設定を上限超過だと
   誤解して1日待つということが起きた

### 確認

環境変数を明示せずに `astro dev` を起動し、`統計学入門` の書名・著者が取得でき、
警告が出ないことを確認した。

## /admin で「取得」を押すと入力が全部消えた — 2026-08-08

### 症状

ユーザーから「ISBNを入れて取得を押したら画面がリセットされる。
もう一度押したらうまくいったが、**2冊目で同じく全ての変更が消える**」。

### 原因

**T28（書影の記録を `.cache/` から `src/data/covers.json` へ移した）の副作用。**

```
取得を押す → 書影URLを src/data/covers.json に記録
           → cover.ts が import しているので Vite のモジュールグラフに載っている
           → HMR が full-reload を投げる → 入力中の記事が消える
```

**2回目にうまくいったのは、1回目で記録済みになり書き込みが起きなかったから。**
症状が「2冊目で必ず再発する」形になっていたのはこのため。

### 直したこと

`astro.config.mjs` の `server.watch.ignored` に入れるだけでは**止まらなかった**。
`cover.ts` の静的 import をやめ、`fs.readFileSync` で読むようにした。
**モジュールグラフに載せないのが確実。**

監視の除外も残してある（`public/covers/` への書き込みも同じ理屈で起きるため）。

外したぶん、dev では `cover.ts` が読む記録が古くなる。
そこで **`/admin` は書いた直後の値を自分で返す**ようにした
（`resolveCoverFor` が `lookupAndRemember` の戻り値をそのまま使う）。
cover.ts に解決させ直すと、いま記録した本が「書影なし」に見えてしまう。

### 確認の仕方

「画面がリロードされて入力が消える」はブラウザ上の現象で curl では見えない。
**Vite の HMR チャンネルに最小の WebSocket クライアントで接続し、
`{"type":"full-reload"}` が飛ぶかを直接見た。**

```
修正前  未記録のISBNを2冊取得 → full-reload が飛ぶ
修正後  同じ操作            → メッセージなし
        記録済み・自前画像・書影なし の3経路でも飛ばない
```

### 途中で踏んだもの

コメントに `**/admin` と書いたところ、`*/` がブロックコメントを閉じて
`astro.config.mjs` が壊れ、dev サーバーが起動しなくなった。
エラーは「Dev server process exited before becoming ready」としか出ず、
原因が分かるまで時間を使った。**glob をコメントに書くときは注意する。**
