## 1. 目的

※ **2026-08-05 コンセプト変更**（business-plan.md に基づく）: 対象を「学術書の入門ガイド」から**「有名ではないが本当に面白い本」の発掘**へ広げた。変えたのは*本の条件*であり、*選者の条件*ではない。

その領域に詳しい人に書いてもらった「**その領域を学ぶための本（3冊以上）**と、その選書理由」を、**選者の実名と文脈つきで**公開する日本語のWebメディア。

**編集方針**: 定番の名著だけでなく、**あまり知られていない良書も積極的に紹介する**。ただし1冊ごとの必須条件にはしない。

- 誰の: 知的好奇心が強く読書量が多い層（大学院生・研究者・編集者・読書習慣のある社会人）で、**すでに有名な本は読み尽くしていると感じている人**
- 何の課題: 年間7万点以上の新刊が出るが、書店の平台・Amazonのランキング・広告に出るのは一部のみで、**良い本が埋もれる構造がある**。現状はX/note/書評/口コミを自力で探索し月数時間かかる
- 解決策の核: **ブクログにない「誰が薦めたか」＝選者の専門性と選書理由**を一次取材で提供する
- **選者の資格（2026-08-05 改定）**: **その領域に詳しい人。肩書きは問わない**（研究者・在野の研究者・編集者・翻訳者・書店員・実務家・その領域を長く読み続けている人）。ただし**「なぜその領域に詳しいのか」の記述（`credentials`）は必須**

### 最優先事項: UI/UX の質（オーナー判断・2026-08-04）

**本プロダクトの差別化の中核は、コンテンツの質と UI/UX の質である。** これは機能追加では代替できない。

根拠:
- 競合 Five Books は17年・1,700本のアーカイブを持つ。**後発が「量」で勝つ経路は存在しない**
- 日本語圏の書評・書籍メディアは UI/UX の水準が総じて低いというのがオーナーの観察であり、ここが唯一の攻めどころになる
- 書影を使えない制約（8参照）は、**タイポグラフィで独自の世界観を作る方向に転換できる**。書影に頼る他メディアと視覚的に差がつく

したがって本プロジェクトでは以下を通常より高い水準で要求する:
- 記事ページの読書体験（本文の組版・行長・行間・書体選択）は、機能実装より優先度が高い
- 「書籍カード」の視覚設計がサイトの識別子となる。**（2026-08-05: 冊数固定をやめたため、識別子はこの視覚設計にいっそう依存する）**ここは使い回しのUIコンポーネントで済ませない
- OGP画像（R4）は「共有されるか」を決めるため、デザイン成果物として扱う
- **デザインは dev-design スキルで design-brief.md を作成してから実装する**（実装しながらデザインを決めない）

### このリリースが達成すべきこと（business-plan.md の検証方法に直結）
90日で一次取材記事10本を公開し、**選者本人がXで共有したくなる品質**を実現すること。
したがって本プロジェクトの最優先事項は多機能さではなく、**記事1本の見た目の質とOGP（X上での見え方）**である。

## 3. 非スコープ（やらないこと）

business-plan.md の非スコープを継承し、技術要件として確定する。

- ユーザー投稿機能・ログイン・認証（**認証機構を一切持たない**）
- フォロー / タイムライン / いいね / コメント等のSNS機能
- 読書記録・進捗管理・本棚機能
- ~~一般小説・ビジネス書のレコメンド~~ → **2026-08-05 撤回。** ジャンルによる制限は設けない（学術書も小説もビジネス書も対象）。条件は「有名ではないこと」と「選者がその領域に詳しいこと」であって、ジャンルではない
- 決済・課金機能
- ネイティブアプリ（Webのみ）
- 管理画面（記事はMarkdownファイルを直接編集する）
- データベース（**永続化層を持たない**）
- ~~全文検索~~ → **2026-08-05 一部撤回。** R17 として「記事メタデータ（分野・選者・書名）に対するクライアントサイド検索」を追加した。**本文の全文検索は引き続き非スコープ**（インデックスが肥大し、静的配信の利点を損なうため）
- 多言語対応
- コメント欄
- **フォームの自前実装**（DB・スパム対策・個人情報の保管責任が発生するため）。問い合わせはメールアドレスの静的掲載、選者応募は**外部フォームサービスの埋め込み**で代替する（R16）

## 4. 制約

- コスト: **無料枠のみ**。月額課金が発生する構成は採用しない
- 開発者スキル: React / Next.js の経験あり
- 記事執筆: Markdownファイル（ローカルまたはObsidianで執筆しリポジトリに配置）
- 規模想定: 記事100本以下、月数千PV
- 記事の書影・書誌データの扱いは著作権・API利用規約の範囲内に収める（要調査事項・下記8参照）

## 5. 非機能要件

- **表示速度**: 記事ページはモバイル回線で1.5秒以内に本文が読める（静的生成を前提とする）
- **SEO**: 記事ページが「〇〇 入門書」等で検索対象になるよう、適切な見出し構造・title・description・構造化データを出力する
- **可用性**: 無料枠のホスティングに準ずる（SLAは求めない）
- **保守性**: 記事の追加が「Markdownファイルを1つ追加してpushする」だけで完結すること。ビルド設定の編集を伴わない
- **アクセシビリティ**: 見出し階層が正しく、本文のコントラスト比がWCAG AA相当を満たす
- **読書体験（最優先）**: 記事本文は1行あたり全角35〜45文字相当に収め、行間・余白・書体を長文の通読に耐える水準で設計する。**「読みやすさ」は主観評価ではなく、design-brief.md で定めた具体的な数値（行長・行間・フォントサイズ・コントラスト比）への適合で判定する**
- **視覚的一貫性**: 色・書体・余白はデザイントークンとして一元管理し、コンポーネント側で個別指定しない

## 6. セキュリティ要件

本プロジェクトは**認証・DB・ユーザー入力・個人情報を持たない静的サイト**であり、攻撃面は極小である。その前提で以下を満たす。

- **認証**: なし。ログイン機構を実装しない（実装しないことが最大のセキュリティ対策）
- **入力検証**: ユーザーからの入力を受け付ける経路を持たない。記事内容は開発者本人が書くMarkdownのみ
- **秘密情報の扱い**:
  - APIキー等が必要になった場合（書誌データAPI等）は環境変数で管理し、リポジトリにコミットしない
  - `.env*` を `.gitignore` に含める
  - リポジトリを公開する場合、コミット履歴に秘密情報が含まれないことをリリース前に確認する
- **依存関係**: 導入する外部パッケージを最小限に保つ。`npm audit` で high 以上の脆弱性がない状態でリリースする
- **Markdownのレンダリング**: 記事は自作コンテンツのみだが、HTMLの生埋め込みを許可する場合はサニタイズを行う（またはHTML埋め込みを禁止する）
- **外部埋め込み**: 将来メール登録フォーム等の外部サービスを埋め込む際は、埋め込み先を明示的に許可する方針とする
- **個人情報**: 取材した選者の氏名・所属は公開情報として扱うが、**掲載前に本人の公開許諾を得ることを運用ルールとする**（技術要件ではなく運用要件だが、事業リスクとして明記）

## 8. 要調査事項（調査エージェント実行中・確定後に本書へ反映）

- **競合 Five Books（fivebooks.com）の実態**: 同一コンセプトの英語メディアが実在する可能性が高い。事実確認と、差別化余地・名称衝突リスクの評価が必要。結果次第で business-plan.md の「差別化」セクションの更新を biz-sparring に差し戻す
### 調査完了（2026-08-04）

- **【確定】無料ホスティングの商用利用可否**: Vercel Hobby は商用利用を公式に禁止（docs、2026-06-16更新）。GitHub Pages も同様に禁止。**無料枠かつ将来の収益化が可能なのは Cloudflare のみ**。→ ホスティングは Cloudflare で確定的（規約由来の制約であり技術選定の余地なし）
- **【方針変更・2026-08-04】書影は条件付きで使用する**（オーナー判断により当初の「使用しない」方針を見直し）:
  - オーナーの判断: 本の見た目は選書の動機として重要であり、書影なしのメディアは訴求力を欠く
  - **openBD の利用条件は「本の販促・紹介目的に限り利用可」であり、選書メディアによる書籍紹介はこの範囲に素直に収まると判断**。収益ゼロの現段階では問題になりにくい
  - **残る懸念**: 将来広告収益を得た段階で「紹介目的」の範囲と言えるか。→ **収益化の検討時に再確認することを条件とする**
  - **設計上の必須条件**: 学術書・専門書・古書は書影データの欠損が想定されるため、**一部に書影がない状態でもデザインが破綻しないこと**。欠損時のフォールバックが「画像が無い箱」ではなく意図的な設計に見えることを要件とする
  - カバレッジは実測を進行中（下記「調査中」参照）。実測値によっては方針を再変更する
  - ISBN を frontmatter に保持する方針は変更なし（表示層の差し替えで移行できる状態を保つ）
  - **【オーナー判断・2026-08-04】書影の取得方針**: APIで取得できるものはAPI経由、**取得できないものは自分で用意した画像を登録して配信する**
    - **リスクの記録**: 画像を自前で保管・配信することは複製権・公衆送信権の行使にあたり、openBD等のホットリンク（出版社側が配信）より権利上のリスクが高い。この点は説明済みであり、オーナーの判断として採用する
    - **緩和策（運用ルールとして別途確定させる）**: ①取材時に出版社へ書影掲載の許諾をメールで取得する（記事あたり数冊なら現実的）②出典・書誌情報を明記する ③削除要請には即応する
    - 実装上の含意: 書影の保管先（リポジトリ内 / ヘッドレスCMS / オブジェクトストレージ）は未定。**当面はリポジトリ内に置く最小構成とし、運用が痛くなった時点でヘッドレスCMSへ移行する**（管理画面の自作は行わない — 認証・DBの導入は非スコープ）
- **【参考・当初の調査結果】書影に関する法的整理**:
  - 国立国会図書館サーチの書影画像提供APIは **2026年3月31日で終了済み**（JPROの利用条件変更が理由）
  - openBD は稼働中だが利用条件が「販促・紹介目的に限る」であり、**広告収益を得るメディアでの利用が許諾範囲に収まる保証がない**。基盤の継続性にも不安あり
  - Google Books API は再配布・課金に関する規約制約とカバレッジ不足
  - Amazon PA-API は規約上クリーンだが、アソシエイト審査通過＋売上実績が継続利用の条件のため立ち上げ期には使えない
  - **書影は装丁として著作物**であり、書名・著者・出版社・ISBN（事実データ）とは法的性質が異なる
  - → 上記の方針変更により、**openBD を第一候補として書影を使用する**（Amazonアソシエイト経由への移行は将来の選択肢として残す）

- **【実測結果・2026-08-05】書影APIのカバレッジは低い**:
  - サンプル10冊で **openBD 2件 / Google Books 0件 / フォールバック 8件**（＝取得率20%）
  - ※サンプル記事のISBNは架空の値のため、これは実データの取得率ではない。ただし **Google Books が日本語書籍で0件**だったことは、代替経路として期待できないことを示す
  - **→ `public/covers/` への手動登録が主経路になる**。書影を出したい書籍については、**出版社への許諾取得という運用コストが実際に発生する**
  - **→ 「書影が欠けた本が混ざっても破綻しない設計」は必須要件のまま**（むしろ欠損が常態になる）
- **【調査中→上記で解決】書影APIのカバレッジ実測**: openBD / Google Books API に対して学術系出版社（岩波・みすず・有斐閣・東大出版会等）の書籍ISBNを実際に投げ、書影取得率を実測中。**この結果がデザインを左右する**:
  - 取得率が高い（8割以上）→ 書影グリッドを主役にした設計
  - 取得率が低い・まだら → 書影とタイポグラフィカードが混在しても成立する設計が必須
  - OGP画像（R4）に「書影を並べたサムネイル」を採用できるかも、この結果次第
- **【確定】OGP画像は静的生成**: 記事がリポジトリ内Markdownである以上、画像内容はビルド時に確定する。Satori + resvg でビルド時に `/og/[slug].png` を出力する。動的生成は不要
  - 追加の運用要件: `twitter:card` は `summary_large_image`、`og:image` は 1200×630・絶対URL。画像には**選者名を最大級のサイズで**入れ、書名は2〜3点＋「他N冊」に間引く（タイムライン上で潰れるため）。**デプロイ後にX Card Validatorを通す運用を必須とする**（画像を後から差し替えても反映されない事故を防ぐ）
- **【確定】競合 Five Books（fivebooks.com）は実在する**:
  - 2009年設立・英語圏・1,700インタビュー超／8,000冊超。「専門家がテーマごとに5冊を選びインタビューで理由を語る」形式で、**本企画とコンセプトがほぼ完全に一致**。日本語版は存在しない
  - 収益構造: Amazonアソシエイトが主軸＋寄付＋Patreon（189人・月$301）。自己申告の制作費は1本$400・週2〜3本（≒月$4,000）。**17年・1,700本を積んでなお寄付が制作費の1割未満**
  - 日本語圏に同型メディアは**存在しない**（確認済み）。HONZ は2024年7月に更新終了、紀伊國屋「書評空間」は2014年終了。ALL REVIEWS は書評アーカイブ、じんぶん堂は出版社主導のPR媒体、Book Bang はアグリゲーターで、いずれも「専門家への取材による5冊選書」形式ではない
  - **→ ニッチは空いているが、空白である理由に「市場性の低さ」が含まれる可能性が高い**
  - **収益に関する重要な示唆**: ALL REVIEWS（実質1人運営・PV20万・アフィリエイト＋広告＋読者課金＋**出版社向け有料アカウント**の4本立て）と じんぶん堂（**出版社の会員社モデル**）が、ともに読者ではなく**出版社側から収益を得ている**。学術書特化なら大学出版部を顧客側に置く設計が現実的な可能性。**→ business-plan.md の「価格」検討材料として biz-sparring に差し戻す価値がある（本requirementsでは扱わない）**
  - **名称リスク**: 日本での商標登録有無は**未確認**（J-PlatPat で第16類・第35類・第41類の確認が必要）。ただし法務以前に、「Five Booksの日本版」と誤認されて独自ブランドが育たず、検索でも fivebooks.com に埋もれるマーケティング上の問題が大きい。**→ 名称は変更必須**

## 9. 確定した技術構成（ユーザー承認済み・2026-08-04）

- **フレームワーク: Astro（Content Collections + MDX）** — 書籍のfrontmatterを Zod で型検証し、`.min(3)` で「3冊以上」をビルド時に強制する（2026-08-05まで `.length(5)` で5冊固定だった）。React経験は island として再利用可能
- **ホスティング: Cloudflare Pages** — 無料枠で商用利用が許容される唯一の選択肢（規約由来の制約）
- **OGP画像: Satori + resvg によるビルド時静的生成** — `/og/[slug].png` を全記事分出力。日本語フォントは Noto Sans JP のサブセット
- **アクセス解析: Cloudflare Web Analytics** — 無料・Cookieless
- **メール配信: 外部サービスの埋め込み**（Buttondown無料枠等。具体的サービスは実装時に確定）
- **書影: 使用しない** — 書誌情報のテキスト＋タイポグラフィベースのカードで構成

### アーキテクチャ

```
[執筆]  Obsidian / エディタで Markdown を書く
           │
           ▼
   src/content/interviews/*.md   ← frontmatter に選者情報 + books[5] + ISBN
           │
           │  git push
           ▼
   [Cloudflare Pages ビルド]
     ├─ Astro Content Collections が Zod でスキーマ検証（3冊以上を強制。違反はビルド失敗）
     ├─ 記事ページ / 一覧ページを静的HTML化
     ├─ Satori + resvg で /og/[slug].png を全記事分生成
     └─ JSON-LD（ItemList + Book）を各記事に埋め込み
           │
           ▼
   [Cloudflare CDN で配信（全て静的ファイル）]
     ├─ 読者 ← X の共有カード経由（主要導線。OGPが効く）
     ├─ 読者 ← 検索エンジン経由（JSON-LD と見出し構造が効く）
     ├─ Cloudflare Web Analytics（Cookieless）でPV・流入元を計測
     └─ メール登録フォーム（外部サービスへ直接POST。当サイトはアドレスを保持しない）
```

**サーバーサイドの処理・DB・認証は一切存在しない。** 実行時に動くコードはメール登録フォームの埋め込みスクリプトのみ。
