# Skrinia

その領域に詳しい人が、**その領域を学ぶための本（3冊以上）**を選んで紹介するメディア。
**あまり知られていない良書も積極的に取り上げる**（編集方針であり、1冊ごとの条件ではない）。

このREADMEを読めばメディアの運用（記事の追加・画像の登録・公開）ができるようにしてある。
事業判断の経緯や設計の根拠は `.dev/` にある（`business-plan.md` / `requirements.md` / `design-brief.md` / `plan.md` / `build-log.md`）。

> **サービス名は Skrinia（スクリニア）に確定した**（2026-08-08）。
> ラテン語 *scrinium*（巻物や書物を収める箱）から。
> 表示名は `src/config.ts` の `SITE.name` 1箇所で管理している。

## 1. すぐ動かす

```bash
npm install
npm run dev      # http://localhost:4321
                 #   記事を作る画面は http://localhost:4321/admin（ローカル専用）
npm run build    # dist/ に静的サイトを生成
npm run preview  # ビルド結果を確認

npm run verify   # push する前にこれ。lint → 型チェック → ビルドを通す
npm run check:links  # 内部リンクが実在するページを指しているか検査する

npm run new:selector                     # 選者をマスタに登録・編集する（対話式）
npm run new:article                      # 記事を作る（対話式・/admin が使えないとき）
npm run check:isbn -- 9784150504106 …    # ISBNの書誌が取れるか実測する
npm run sync:covers                      # 書影URLを引いて src/data/covers.json に記録する
```

技術構成: **Astro**（静的生成）/ **Tailwind CSS v4** / **Cloudflare Pages**（無料枠で商用利用が許されるため）。
**データベース・管理画面・ログイン機能は無い。** 記事はMarkdownファイルで管理する。

## 2. 記事を書いて公開する

作り方は2つある。**どちらで作っても出来上がるファイルは同じ**
（生成処理は `scripts/lib/article-file.mjs` に集約してある）。

| | 向いている場面 |
|---|---|
| **画面（`/admin`）** — 推奨 | ふつうはこちら。**長文まで書ける**・選び直せる・分野の絞り込みが速い |
| CLI（`npm run new:article`） | 画面が壊れたとき、手が離せないとき（frontmatter の雛形まで） |

### 画面を使う（推奨）

```bash
npm run dev
# → http://localhost:4321/admin を開く
```

**ローカル専用の画面。** 本番サイトには存在しない（後述）。

1. **編集する記事**を選ぶ。**下書きと公開済みが分かれて**並ぶので、
   開き直して続きから書ける。新しく書くなら「新しく作る」のまま。
   - 下書きは**最後に触った順**、公開済みは公開日の順。
     書きかけを探すときに効くのは更新の新しさで、公開済みは
     いつ出した記事かで思い出すため、並べ方を変えてある
   - 件数が増えたら**絞り込み欄**に打つ（タイトル・分野・タグ・選者で引ける）
2. **選者**を選ぶ
3. **大トピック**を選ぶと、**その配下の小トピックだけ**が候補に出る
4. **タグ**は打った語で絞って選ぶ（いくつでも）
5. **タイトル**は雛形を押して入れてもいいし、自由に書いてもいい
6. **説明（description）**を書く（100〜120字）
7. **ISBN13** を入れて「取得」を押すと書誌が入る。**その場で直せる**。
   同時に**書影が出るかどうかも分かる**（サムネイルと、どこから取れたか）
8. 書影が取れなかった本は、**許諾済みの画像をその場で置ける**（次項）
9. 各冊の**選書理由**（300〜600字）と、印を付けた1冊の
   **なぜ知られていないのか**（150〜300字）を書く
10. **本文**（導入文とまとめ）を書く。書籍カードの上に一続きで置かれる
11. 「保存する」で `src/content/interviews/<slug>.md` に書き出される

**文字数は目安で、外れても保存できる**（何字が適量かは書いてみないと分からないため）。
空欄のまま保存すれば `TODO:` の枠が入り、`draft: false` にした時点でビルドが指摘する。

**自動保存はしない。** 保存は「保存する」を押したときだけ。
書きかけが静かに上書きされるより、押し忘れの方が取り返しがつく。

**読み込んだあとにファイルが外で変わっていたら、保存前に確認が出る。**
（ビルドが落ちてエディタで直した、`git pull` した、など）。
そのまま上書きするか中止するかを選べる。

**削除機能は無い。** 消すときはファイルを消す。

#### 書影を確かめて置く

「取得」を押すと、その本の書影が**サムネイルとして出る**。
どこから取れたか（自前 / openBD / Google Books）も出るので、
**自前の画像を用意すべき本かどうかがその場で分かる。**
書影が出るかどうかをビルドまで待たずに済むのは、
取れないと分かってから許諾を取りに行く時間を残すため。

取れなかった本は、画像を選んで「この画像を置く」で
`public/covers/<ISBN>.<拡張子>` に保存され、**表示がその場で切り替わる。**
置ける形式は `.jpg` `.jpeg` `.png` `.webp`（`src/lib/cover.ts` が認識する形式そのもの）。
画像は**変換もリサイズもせず、渡したまま**保存される。

- 拡張子を偽ったファイルは弾かれる（先頭バイトで実体を確かめている）。
  置けてしまうと、壊れた書影がそのまま本番に出る
- 同じISBNの画像が既にあれば**確認が出る**。拡張子違いのファイルは、
  上書きのときに削除される（`.jpg` と `.png` が両方残ると
  `.jpg` が勝ち、**置いたはずの画像が出ない**）

**書影URLは `src/data/covers.json` に記録され、リポジトリに入る。**
ビルドも dev も、この記録を読むだけで**外部APIを叩かない**。
引くのは「取得」を押したときと `npm run sync:covers` を叩いたときだけ。

以前は表示のたびに引いていたため、Google Books の1日あたりの上限
（無料枠 1,000件/日）を使い切ると**書影が一斉に消えた**。
本番ビルドは Cloudflare 上で走るので、手元では見えているのに
**本番だけ落ちる**ということも起こりうる。

```bash
npm run sync:covers              # 記録の無い本だけ引く
npm run sync:covers -- --force   # 記録済みも引き直す（URLが腐ったとき）
```

**429 やタイムアウトは記録しない。**「今は答えられない」を
「書影が無い」として焼き付けると、本当は書影がある本が出なくなるため。
その日は取れなかった本として残り、日を改めれば引ける。

> **置いた画像は自サイトから配信される。** 外部APIのURLを参照するのとは違い、
> 書影の複製・公衆送信にあたり、**出版社の許諾が要る**。画面にも同じ警告が出るが、
> **操作は妨げていない**（許諾の有無は画面では判定できないため）。
> 運用ルールは [`docs/covers.md`](docs/covers.md)。

> #### この画面が本番に出ない理由
>
> 記事ファイルを書き込む口を持つので、公開されると困る。守りは3つある。
>
> 1. 裏側の API は **Vite の `apply: "serve"` プラグイン**
>    （`scripts/lib/admin-dev-server.mjs`）。**ビルドでは読み込まれもしない**
> 2. `npm run build` の後に `scripts/strip-admin.mjs` が `dist/` から `/admin` を消す
>    （消えたことをログに出し、残っていればビルドを失敗させる）
> 3. 画面自体も `import.meta.env.DEV` を見て、開発時以外は中身を描画しない
>
> sitemap からも除外している（`astro.config.mjs`）。
> 除外しないと、消したはずのURLを sitemap が申告し続けて 404 が Search Console に出る。

### CLIを使う

```bash
npm run new:article
```

対話形式で以下を聞かれ、`src/content/interviews/<slug>.md` が生成される。

1. **テーマ** — 一覧から選ぶ（新規追加もできる）
2. **選者** — マスタから選ぶ（その場で新規登録もできる）
3. **冊数** — 3以上を入力する（Enterで5）。タイトルの雛形とISBNの入力回数に使われる
4. **記事タイトル** — 雛形3案から選ぶか、自由に入力する（自動生成はしない）
5. **検索用タイトル**（任意）と **slug**（半角英数のみ）と **要約**
6. **ISBN13 を冊数分** — 入れるだけ。書誌は自動取得される

**ターミナルで長文は書かない。** 選書理由と導入文は
`TODO:` のプレースホルダで出力されるので、**エディタで書く**。
ターミナルは一度打つと戻れず、修正もできないため。

### 書き上げるまでの流れ

```
/admin か npm run new:article  → 雛形ができる（draft: true）
      ↓
/admin で開き直して TODO: を埋める、書誌を確認する（エディタで書いてもよい）
      ↓
npm run dev             → 見た目を確認（下書きも表示される）
      ↓
draft: false にする
      ↓
npm run build           → 未記入が残っていれば「何冊目のどの項目か」を指して落ちる
```

**書誌の自動取得は openBD と Google Books の両方を引き、項目ごとに良い方を採る。**

| 項目 | 優先 | 理由 |
|---|---|---|
| 書名・著者 | **Google Books** | openBD は叢書名・巻次・副題が混ざり、著者は図書館形式（`Locke,John,1632-1704`） |
| 出版社 | **openBD のみ** | Google Books は返さない（実測 0/10） |
| 刊行年 | 取れた方 | 食い違えば要確認コメントに出す |

**どちらか一方が常に正しいわけではない。** 実測では Google Books が
「日本/権力構造の謎上」と空白を落とすこともあった。だから候補が食い違ったときは
両方を要確認コメントに書き出している。
**機械では正解を選べない箇所**（書名の食い違い・刊行年の不一致・volume の混入）は、
生成ファイルの冒頭にコメントとして書き出されるので、そこを見て直す。

### 手で書く場合

1. `src/content/interviews/` に `.md` ファイルを1つ作る
2. frontmatter を書く（[全項目は §3](#3-frontmatter-の全項目)）
3. `git push` する → Cloudflare Pages が自動でビルド・公開

**ファイル名は自由**（URLには影響しない）。慣例として `<選者のID>-<テーマ>.md` にしている。
例: `yamada-taro-behavioral-economics.md`

**URLは frontmatter の `slug` で決まる。** `slug: yamada-behavioral-economics` なら
記事URLは `/yamada-behavioral-economics/` になる。

### 記事の本文について

frontmatter の外（`---` の下）に書いたMarkdownが、**書籍カードの上に置かれる導入文**になる。
まとめの文章もここに書く。段落・見出し（`##`）・引用（`>`）が使える。

各書籍の説明は本文ではなく **frontmatter の `reason`** に書く。
本文に書いてもカードには表示されない。

### 最小の記事テンプレート

```markdown
---
title: 山田太郎が選ぶ、行動経済学の5冊
seoTitle: 行動経済学の入門書5冊 — 山田太郎が選ぶ   # 任意。検索結果の <title> だけ差し替える
slug: yamada-behavioral-economics                  # 半角小文字英数とハイフンのみ
publishedAt: 2026-08-04
description: 一覧・検索・OGP・meta description に使われる要約。120字程度。
topic: 行動経済学        # src/data/topics.json にある語彙のみ
selector: yamada-taro   # src/data/selectors.json のキー
keywords:
  - 行動経済学
  - 意思決定
books:
  - title: ファスト＆スロー（上）
    author: ダニエル・カーネマン
    translator: 村井章子
    publisher: 早川書房
    year: 2014
    isbn: "9784150504106"
    reason: |
      なぜこの本を薦めるのか。300〜600字。
  # ここに残りの本を書く。**合計3冊以上**（上限なし）
---

導入文をここに書く。選者がどういう人で、この数冊で何が見えるのか。3〜5段落。

> 選者の発言を引用として置くこともできる。

まとめもここに書く。
```

### 選者に寄稿を依頼するときのテンプレート

`.dev/business-plan.md` で「**寄稿がデフォルト、相手が望めば取材も受ける**」と決めている。
依頼時は以下を必ず伝えること。

- **3冊以上**（上限なし。2冊以下はサイトがビルドできない）
- 各冊の**選書理由**（300〜600字）
- **「この中でいちばん知られていない本はどれですか」** — 1冊選んでもらい、なぜ知られていないかを150〜300字（**必ず聞くこと**。任意項目なので聞かないと集まらない）
- 選者ご自身の**所属・略歴・その領域に詳しい理由**
- Xアカウント（任意。露出になるので聞いておく）
- 「読みやすさのため体裁を整えさせていただく場合があります」と**事前に伝える**
- **掲載前に校正稿を送って本人に確認してもらう**（下記）

### 掲載前の確認（必須）

**公開する前に、必ず本人へ校正稿を送って了承を得ること。**

```
draft: true のまま書き上げる
      ↓
npm run dev で表示を確認し、記事のURLか本文を本人へ送る
      ↓
本人の了承を得る（メールで記録を残す）
      ↓
draft: false にして公開
```

理由は3つある。

1. **選者は実名でなくてよい**（ハンドル名と「詳しい理由」だけでも掲載できる）。
   本人確認の手段が限られるぶん、**本人が内容を見て了承した記録**が唯一の担保になる
2. 選書理由は体裁を整えて掲載するため、**意図が変わっていないかは本人にしか判断できない**
3. 所属・肩書きの表記は本人の希望が優先される（変わっていることもある）

**連絡先（メールアドレス）は、応募・依頼の時点で必ず受け取っておくこと。**
サイト上は匿名でよいが、送り先が無いと校正稿を送れず、
訂正や削除の要請にも応えられない。

## 3. frontmatter の全項目

ビルド時に型チェックされる（`src/content.config.ts`）。
**必須項目が欠けている・3冊未満・ISBNの形式が違う場合、ビルドが失敗して公開されない。**
壊れた記事が本番に出ることはない。

### 記事本体

| 項目 | 必須 | 型 | 説明 |
|---|---|---|---|
| `title` | ✅ | 文字列 | 記事タイトル。**H1・OGP・X共有カード**に使われる |
| `seoTitle` | — | 文字列 | **検索結果に出る `<title>` だけ**を差し替える。未指定なら `title` が使われる。※下記参照 |
| `slug` | ✅ | 文字列 | URLになる。**半角小文字の英数とハイフンのみ**（日本語不可）。※下記参照 |
| `draft` | — | 真偽値 | **既定は `false`（公開）。** CLI が作る雛形には `draft: true` が入る。`true` のあいだは `TODO:` が残っていてもビルドが通り、**本番には出ない**（開発サーバーでは表示される）。書き上がったら `false` にする |
| `publishedAt` | ✅ | 日付 | `2026-08-04` 形式。並び順に使う |
| `updatedAt` | — | 日付 | 内容を直したときに入れる。JSON-LD の `dateModified` に使われる |
| `description` | ✅ | 文字列 | 一覧・検索・OGP・meta description。120字程度 |
| `topic` | ✅ | 文字列 | **大トピック。** `topics.json` にある語彙のみ。**ページが生成される**（`/topics/<名前>/`） |
| `subtopic` | — | 文字列 | **小トピック。** その大トピックに属する語彙のみ。ページは作らず検索で引く |
| `tags` | — | 文字列の配列 | **タグ。** 小トピックより細かいもの。`tags.json` にある語彙のみ。※下記参照 |
| `keywords` | — | 文字列の配列 | SEO用 |
| `selector` | ✅ | 下記 | 選者 |
| `books` | ✅ | 下記 × **3件以上**（上限なし） | 紹介する本 |

### `selector`（選者）— **記事には書かない。マスタをIDで参照する**

記事の frontmatter には `selector: yamada-taro` のように**IDだけ**を書く。
実データは `src/data/selectors.json` にある。

**所属や略歴が変わったらマスタ1箇所を直せば全記事に反映される。**
記事ごとにコピペすると、変更のたびに全記事を直すことになるため分離してある。
選者ページのURLもこのID（`/selectors/yamada-taro/`）。

```json
{
  "yamada-taro": {
    "name": "山田太郎",
    "reading": "やまだ たろう",
    "affiliation": "○○大学 経済学部 教授",
    "bio": "どういう研究をしている人かを1〜2文で。",
    "credentials": "なぜこの領域に詳しいのか。研究・仕事・発信・読書歴など、形式は問わない。",
    "avatar": "yamada-taro.jpg",
    "links": { "x": "yamada_t", "site": "https://example.ac.jp/yamada" }
  }
}
```

| 項目 | 必須 | 説明 |
|---|---|---|
| キー（ID） | ✅ | 半角英数とハイフン。**URLになる** |
| `name` | ✅ | 氏名 |
| `reading` | — | ふりがな |
| `affiliation` | — | 所属。**任意**。大学の教員だけを選者にするわけではないため必須にしていない。無ければ代わりに `credentials` が表示される |
| `bio` | ✅ | 略歴 |
| `credentials` | ✅ | **この人が詳しい理由。** 「なぜこの人の推薦を信じるのか」の根拠。**肩書きや形式は問わない**（研究・仕事・発信・読書歴など）。※下記参照 |
| `avatar` | — | 顔写真のファイル名。`public/selectors/` に置いた画像を指す。**未登録なら頭文字のアバターが出る**ので、写真の有無でレイアウトは崩れない |
| `links.x` | — | Xのハンドル。**`@` は付けない**（`yamada_t` と書く） |
| `links.site` | — | 個人サイト等のURL |

**登録されていないIDを書くとビルドが失敗する。**

### 選者の登録・編集

```bash
npm run new:selector
```

新規登録と、既存選者の編集ができる。**所属や略歴が変わったらここから直せば全記事に反映される。**
記事作成（`npm run new:article`）の途中でも新規登録できるが、選者はマスタなので
**記事を書く前に単独で登録しておける。**

> **IDは変更できない。** 変えるとURL（`/selectors/<id>/`）が変わり、公開済みのリンクが切れる。

#### `credentials` を必須にしている理由

選者は**学者に限らない**。在野で研究を続けている人、その領域を長く読み続けている人、
編集者・書店員・実務家も含む。**肩書きは問わない。**

ただし「なぜその領域に詳しいのか」は必ず書く。**選者の知名度がゼロの初期段階では、
ここが読者にとって唯一の手がかりになる**ためで、空だと「知らない人のおすすめリスト」に
なり、ブクログのレビューと区別がつかなくなる（差別化の中核が消える）。

書き方の例:

- 「〇〇について15年読み続けている。△△という同人誌で書評を書いている」
- 「△△出版で人文書の編集を担当。〇〇シリーズを手がけた」
- 「〇〇に関する論文が△△誌に掲載。□□学会の企画委員」
- 「在野で〇〇史を調べており、Xで継続的に書いている」

### `books`（必ず5件）

| 項目 | 必須 | 説明 |
|---|---|---|
| `title` | ✅ | 書名 |
| `author` | ✅ | 著者 |
| `translator` | — | 訳者。あれば「著者 / 訳者 訳」と表示される |
| `publisher` | ✅ | 出版社 |
| `year` | ✅ | 刊行年（数値。`2014` のようにクォートなし） |
| `isbn` | ✅ | **ハイフンなしの13桁。必ずクォートで囲む**（`"9784150504106"`） |
| `reason` | ✅ | 選書理由。300〜600字 |
| `whyBuried` | — | **この本があまり知られていない理由。** 書くと「知る人ぞ知る本」の印が付き、[`/hidden`](#知る人ぞ知るhidden) に集まる。※下記参照 |

### 知る人ぞ知る本（`/hidden`）

`whyBuried` を書いた本は `/hidden`「知る人ぞ知る本」に、**分野を横断して**集まる。

```yaml
- title: 公式と例題で要点を掴む多変量解析
  reason: |
    複雑になる多変量解析に関する専門書。…
  whyBuried: |
    2026年刊行の新しい本で、まだ書評もほとんど出ていない。…
```

**1記事につき1冊、任意。** 全冊に必須にすると定番書の記事が書けなくなるため
（実際に1本目で詰まった）、**1冊だけに絞ってある**。書かなければ何も起きない。

**なぜこのページが要るか**: 記事はテーマごとに縦に切られているので、
その分野に興味がない読者には届かない。`/hidden` は横に切るため、
分野を問わず読める。**Amazon にも書店の平台にも作れない**（ランキングは
売れている順なので、原理的に埋もれた本を出せない）。**記事が増えるほど資産になる。**

判定は**選者本人の主観でよい**。「この中でいちばん知られていないのはどれですか」
には必ず答えられる。

> **依頼時に必ず聞くこと。** 任意項目なので、聞かないと永遠に集まらない。

### `title` と `seoTitle` を分けている理由

記事タイトルは `〈選者名〉が選ぶ、〈テーマ〉のN冊` のような形で、**X共有時に「誰が選んだか」を伝えるためのもの**。差別化の中核が「選者の実名と専門性」なので、共有文から選者名が消えてはいけない。

一方、検索する人が打つのは「**行動経済学 入門書**」「**行動経済学 おすすめ 本**」であり、`〜が選ぶ、〜のN冊` にはこれらの語が含まれない。

そこで**検索結果に出る `<title>` だけ**を差し替えられるようにしてある。

```yaml
title:    山田太郎が選ぶ、行動経済学の5冊          # H1・OGP・X共有
seoTitle: 行動経済学の入門書5冊 — 山田太郎が選ぶ    # <title>・検索結果
```

**任意項目なので、書かなければ `title` がそのまま使われる。** 検索を意識したい記事だけ書けばよい。

### `slug` は半角英数のみ（日本語不可）

**日本語を使うとURLがエンコードされて長大化する。**

```
✗ /yamada-taro-行動経済学/  → /yamada-taro-%E8%A1%8C%E5%8B%95%E7%B5%8C%E6%B8%88%E5%AD%A6/
✓ /yamada-behavioral-economics/
```

**Xでの共有が主要導線**なので、URLが読めない文字列になるのは実害が大きい。
またスキーマで弾いているのは、**一度公開したURLは変えられない**ため（変更するとリンク切れと検索評価のリセットが起きる）。

なおテーマページ（`/topics/行動経済学/`）は日本語のままでよい。回遊用であり、共有される導線ではないため。

### 分類は3階層（大トピック / 小トピック / タグ）

```yaml
topic: 数学              # 大トピック（必須・1つ）  → /topics/数学/ が生成される
subtopic: 統計学         # 小トピック（任意・1つ）  → ページなし・検索で引く
tags:                    # タグ（任意・複数）       → ページなし・検索で引く
  - 数理統計学
  - 多変量解析
```

**「数学」と「解析学」はレイヤーが違う**のに単一軸だと同じ場所に並び、登録のたびに
どちらのレベルで入れるか迷う。放置すると粒度の違うページが `/topics/` に混在する。
そこで階層を分けた。

| | `topic` | `subtopic` | `tags` |
|---|---|---|---|
| 必須 | ✅ | — | — |
| 数 | 1つ | 1つ | 複数 |
| 語彙 | `topics.json` | `topics.json` の該当 topic 配下 | `tags.json` |
| **ページ** | **`/topics/<名前>/`** | **作らない** | **作らない** |

**小トピックとタグにページを作らない理由**: 記事が少ないうちは**1記事しか無いページが
量産される**。薄いページはインデックスされにくく、回遊にも寄与しない。
**検索で引ければ用は足りる**（記事ページからも `/search?q=<語>` にリンクしている）。
記事が増えて1語あたり複数記事になったら、ページ化を検討する。

**小トピックは大トピックとの組で検証される。** 「天体物理学」は物理学にも天文学にも
あるように、学際分野は複数の大トピックに属する。全体で一意ではない。

### `tags` に人名を入れてよい範囲 — **哲学者だけ**

**原則は「人名はタグにしない」。例外は哲学者に限る。**

もともと人名は一律で落としていた（記事21本・19本を作ったとき、グロービス / 東京大学 /
ブレイディみかこ / 木庭顕 / ラマチャンドラン などを落とした）。タグは**分野を横断して
記事を引くための語彙**であって、その記事に出てくる固有名の置き場ではないため。

哲学だけこれを覆した。**哲学では人名が事実上の分野名として機能する**からで、
「スピノザを読むならどの本か」「カント入門は何か」という引き方が実際に成立する。
小トピック（`哲学史` `倫理学` `形而上学` …）は**問いの領域**を切るが、
人物では切れない。役割が重ならないので両方置ける。

他の学問はそうならない。「ラマチャンドランの本」を探す人はいるが、それは
**著者検索**であって分野の横断ではない。同じ理由で、研究者・作家・機関名は入れない。

| | 入れる | 入れない |
|---|---|---|
| 人名 | 哲学者（西洋・東洋・日本）| 研究者 / 著者 / 作家 / 機関名 / 書名 |

**「哲学者」の線**は「哲学（形而上学・認識論・倫理学・存在論など）を主題として著作を残し、
**日本語で読める入門書か翻訳がある**人物」。日本語の本が無い人物のタグを作っても、
このメディアでは引っかかる記事が生まれない。啓蒙思想家・社会科学者は線の外に置いた
（福沢諭吉やアダム・スミスを入れていないのはこのため）。

**表記は1人につき1つ。** 日本語で定着している側を採る。

- **姓のみが慣例**の人物は姓のみ（`カント` `ヘーゲル` `デカルト` `スピノザ` `ニーチェ`）
- **姓だけでは他人と紛れる**人物はフルネーム（`フランシス・ベーコン`＝ロジャー・ベーコンと
  区別 / `トマス・クーン` `ウィリアム・ジェイムズ` `ジョン・スチュアート・ミル`）
- 欧文のフルネームは**中黒**でつなぐ（`マルクス・アウレリウス`）。
  ただし**原語がハイフンの複合姓は `=`**（`メルロ=ポンティ` `レヴィ=ストロース`）
- 日本・中国の人物は中黒を使わず、そのまま（`西田幾多郎` `荻生徂徠` `朱熹`）

### 語彙はどこから来たか

`docs/topic.md`（学問の一覧）から抽出し、`docs/topics-list.md` に整理してある。

- 大トピック **31** / 小トピック **919** / タグ **423**
- 各分野の「〇〇史」は歴史学から**それぞれの学問へ移した**（経営史→経営学 など）
- 「統計学」は元データに無かったため**数学の小トピックとして追加**した

**新しい語彙は `npm run new:article` の中で追加できる。** 小トピックが919件あるため、
CLI は**大トピックを選ぶと配下の小トピックだけを出す**。タグは**入力した語で絞り込む**。

### `topic` は語彙が閉じている

`src/data/topics.json` に定義した語彙しか使えない。**未登録の値を書くとビルドが失敗する。**

```json
{
  "行動経済学": { "description": "" },
  "科学史": { "description": "意思決定の歪みと制度設計をめぐる読書案内" }
}
```

**`description` は任意。** 書くとテーマページに表示され、`meta description` にも使われる。
記事が増えるとテーマページが「〇〇 おすすめ本」のような検索の受け皿になるが、
**記事リストだけのページはインデックスされにくい**ため、書けるテーマには入れておくとよい。

自由入力にすると「行動経済学」「行動経済学入門」「行動経済学 」のように表記が揺れ、
アーカイブページが乱立する。新しいお題を立てるには topics.json への追記が必要で、
**その一手間が「本当に新しいテーマか」を考える抑止として機能する。**

追加は `npm run new:article` の中でできる（確認事項が表示される）。

### `topic` は「分野」ではなく「お題」

記事タイトルの型が `〈選者〉が選ぶ、〈topic〉のN冊` なので、**`topic` には分野名も企画名も入る。**

- 分野: `行動経済学` `科学史` `中世哲学`
- 企画: `自分のバイブル` `絶版だが読まれるべき本`

どちらも `/topics/<topic>/` が自動生成され、検索にも乗る。**専用の仕組みは要らない。**

> **企画のお題を立てるときの注意**
>
> このメディアの価値は「**その道に詳しい人しか知らない本**」にある。
> お題を立てるときは、次の2つが保たれているか確認すること。
>
> - **なぜこの人に聞くのか**（選者の専門性が必要なお題か）
>
> 例: ❌「自分のバイブル5冊」— 誰でも語れて、有名な本が並ぶ
> ✅「この分野に入る前に読んでおけばよかった5冊」— 専門性が要る
> ✅「絶版だが読まれるべき本」— コンセプトの中心

**同じ企画を3本以上続けるなら**、`topic`（分野）と `series`（企画）を分ける構造を検討する。
1〜2本のうちは `topic` に企画名を入れるだけでよい（使われないフィールドを増やさない）。

**タグ機能はない。** 分類軸は `topic` の1つだけ。
`keywords` は JSON-LD に入るだけで、ページも UI 表示もない。

**`isbn` は書影の取得と将来のリンクに使う結合キー。** 書影を出さない本でも必ず正しい値を入れること。

書く時点で「なぜ埋もれているのか」を説明する必要があるので、自然にフィルタが働く。

## 4. 画像の置き場所

**画像は原則すべて任意。** 用意しなくてもサイトは成立するように作ってある。

| 種類 | 置き場所 | ファイル名 | 用意しない場合 |
|---|---|---|---|
| **書影** | `public/covers/` | `<13桁ISBN>.jpg` | 書名を**縦組み**にした面が出る（和書の装丁のように見える） |
| **記事サムネイル** | `public/thumbnails/` | `<slug>.jpg` | その記事のOGP画像を自動で流用する |
| **OGP画像** | — | — | **自動生成**。用意不要 |
| **選者の顔写真** | `public/selectors/` | 任意（`avatar` で指定） | **頭文字の円形アバター**が出る |

`.jpg` `.jpeg` `.png` `.webp` を認識する。原則 `.jpg`。

### 書影の登録: `public/covers/9784150504106.jpg`

書影は以下の順で解決される。**上にあるものが優先される。**

1. `public/covers/<ISBN>.jpg`（自分で登録した画像）
2. openBD API
3. Google Books API
4. 縦組みの書名（フォールバック）

ビルドすると**書影がなかった本がISBN付きで一覧表示される**ので、そのままコピーして画像を用意できる。

```
[cover] 15冊 — 自前 1 / openBD 4 / GoogleBooks 6 / フォールバック 4
  書影なし（public/covers/<ISBN>.jpg に置くと反映されます）:
    9784784212873  実験機器と職人の科学史
    9784622095804  科学革命の構造
```

開発サーバーでは**画像を置いてリロードすれば即反映される**（再起動は不要）。

**実測の傾向**: 流通中の本なら7割前後は自動で取れるが、**このメディアが本命とする
「絶版・少部数の埋もれた本」ではほぼ取れない**（書影は販促用のデータなので、売っていない本には用意されない）。
書誌データは刊行年に関係なく残るのに対し、書影だけがこの偏りを持つ。

つまり**扱う本が狙いどおりであるほど、書影は自分で登録することになる。**
縦組みのフォールバックは例外ではなく標準的な見た目として設計してある。

> ### ⚠️ 書影の登録には出版社の許諾が必要
>
> `public/covers/` に置いた画像は自サイトから配信される。これは表紙デザインの
> **複製および公衆送信**にあたり、外部APIのURLを参照するのとは法的な扱いが違う。
>
> 1. **出版社へ書影掲載の許諾をメールで取得する**（掲載先URL・用途・期間を明記し、返信は保存する）
> 2. **書誌情報と出典を記事に明記する**（自動で表示される）
> 3. **削除要請には即応する**（該当ファイルを消して再デプロイ。窓口は `/contact`）
>
> **許諾が取れていない書影を置かないこと。** 詳細は `docs/covers.md`。

### 記事サムネイルの登録: `public/thumbnails/<slug>.jpg`

トップページの記事カード（236×150）に使われる。
**用意しなければOGP画像が自動で使われる**ので、通常は不要。

## 7. 品質管理（CI・Linter）

### コマンド

| コマンド | 内容 |
|---|---|
| `npm run verify` | **push 前にこれを実行する。** lint → 型チェック → ビルドを順に通す |
| `npm run lint` | Biome でチェック（フォーマット + Lint） |
| `npm run lint:fix` | 自動修正できるものを直す |
| `npm run format` | フォーマットだけかける |
| `npm run typecheck` | `astro check` による型チェック |

### Linter: Biome

フォーマットとLintを1つでまかなう（ESLint + Prettier の代わり）。設定は `biome.json`。

**`.astro` ファイルは Lint の一部を無効にしてある。** Biome は Astro のテンプレート部分を解析できず、
テンプレート内でしか使っていない import を「未使用」と誤検出するため。
`.ts` / `.json` / `.css` は通常どおりチェックされる。

### CI: GitHub Actions

`.github/workflows/ci.yml`。**push と Pull Request のたびに自動で走る。**

| ステップ | 何を防ぐか |
|---|---|
| Lint（Biome） | コード品質のばらつき |
| 型チェック | 存在しないフィールドの参照など |
| **ビルド** | **記事の不備。3冊未満・ISBNの形式違い・必須項目の欠けはここで落ちる** |
| 生成物の健全性チェック | 下記4点 |
| 脆弱性チェック | 依存の既知の脆弱性（警告のみ。CIは落とさない） |

**生成物の健全性チェックで見ているもの:**

1. **外部CDNへの参照がない**こと（フォントのセルフホストが壊れていないか）
2. **色の直書きがない**こと（`text-[#2F4A3F]` のようにトークンを迂回していないか）
3. **書影のフォールバックが "No Image" になっていない**こと
4. **記事数とOGP画像の数が一致**していること、sitemap・検索インデックスが生成されていること

2番目は特に重要。Tailwind は任意値記法で簡単にトークンを迂回できてしまい、
放置すると色や余白が少しずつばらついて「洗練」が壊れる。**機械的に止めている。**

### CI と Cloudflare Pages の役割分担

- **CI**: main にマージする**前**に落とす。壊れた記事が本番に出るのを防ぐ
- **Cloudflare Pages**: main にマージされた**後**にビルドして公開する

両方でビルドが走るが、目的が違う。

## 8. デプロイ

**Cloudflare Pages**（無料枠で商用利用が許されている。Vercel HobbyとGitHub Pagesは規約で商用利用を禁止しているため使えない）。

1. Cloudflare ダッシュボードで Pages プロジェクトを作り、このリポジトリを接続する
2. ビルド設定
   - ビルドコマンド: `npm run build`
   - 出力ディレクトリ: `dist`
3. 環境変数に `PUBLIC_CF_BEACON_TOKEN` を設定する
4. `git push` すると自動でビルド・公開される

## 10. よくある詰まりどころ

### ビルドが `books は3冊以上にしてください` で失敗する
**書籍が2冊以下になっている。** これは仕様。3冊未満では「選書」として成立しないため、
型レベルで最低冊数を強制している（上限はない）。

> 以前は `.length(5)` で5冊ちょうどを強制していたが、2026-08-05 に3冊以上へ緩和した。
> 経緯と失うもの（識別子としての固定形式）は `.dev/business-plan.md` に記録してある。

### ビルドが `isbn は13桁の数字のみ` で失敗する
ISBNにハイフンが入っているか、クォートで囲んでいない。
`isbn: "9784150504106"` の形にする（`978-4-15-050410-6` は不可）。

### 書影が出ない
仕様どおり。**実測で8割の本は自動取得できない。** 出したい場合は許諾を取ったうえで
`public/covers/<ISBN>.jpg` に置く。置かない場合の縦組み表示は「壊れ」ではなく意図した見た目。

### 分野ページのURLに日本語が入る
仕様。`/topics/行動経済学/` のように日本語のまま扱っている（リンク生成時にURLエンコードされる）。

### 選者ページが分かれてしまう / 統合されてしまう
選者の同一性は **`selector.name` の完全一致**で判定している。
表記を揺らすと別人になり、同姓同名は同一人物になる。

### OGP画像を修正したのにXで古いまま
Xがカード画像を強くキャッシュしているため。**Card Validator でキャッシュを更新する**か、
`slug` を変えて別URLにする。これを避けるため、**初回公開時に必ず Validator を通すこと。**

### 選者の顔写真: `public/selectors/<ファイル名>`

`src/data/selectors.json` の `avatar` にファイル名を書くと表示される。

```json
{ "yamada-taro": { "avatar": "yamada-taro.jpg", "...": "" } }
```

**必須にしていない。** 研究者は写真の提供を渋る場合があり、必須にすると
取材のたびに交渉が発生する。

#### 未登録のときの表示

| 状態 | 表示 |
|---|---|
| `avatar` を指定 | その画像 |
| 未指定で `public/selectors/_default.jpg` が**ある** | その既定画像（全員共通） |
| 未指定で既定画像も**ない** | **氏名の頭文字**を円形に出す |

**既定画像はファイルを置くだけで切り替わる**（設定は不要）。
ファイル名は `_default.jpg` / `.png` / `.webp` のいずれか。

> **どちらがよいか**: 既定画像を置くと、写真のない選者が**全員同じ見た目**になる。
> 頭文字は人ごとに変わるので、一覧での識別性は頭文字の方が高い。
> 好みで選んでよいが、選者が増えるほど差が出る。

画像は正方形に切り抜かれる（`object-fit: cover`）。推奨は 200×200px 以上。
