# 選者応募フォームの設計

`/apply` から飛ばす応募フォームの中身。**Tally にそのまま入れられる形**で書いてある。

作ったら URL を `src/config.ts` の `applyFormUrl` に入れる。空のあいだは
`/apply` に「準備中です。メールでご連絡ください」と出る。

**X などで直接声をかけるときの文面と原則は `docs/outreach.md`。**

---

## なぜ Tally か

`.dev/requirements.md` の R16 で決めている。自前実装しないのは、
**DB・スパム対策・個人情報の保管責任**が発生するため。外部に持たせれば、
回答は Tally 側に溜まり、こちらはメール通知を受け取るだけで済む。

Google フォームを避けたのは2つの理由。

- **CI が `gstatic` への参照を弾く**（`.github/workflows/ci.yml`）。
  Google フォームを埋め込むとここに当たる可能性が高い
- 見た目がサイトのトーンに馴染まない

---

## 設計の原則

**項目は記事の frontmatter と一致させる**（R16a）。応募内容がそのまま
記事の素材になり、往復のやり取りが減る。運用工数に直結する。

**書いてもらう量を最小にする。** 選書理由は**100〜200字程度**でよいことにし、
上限も「最大でも600字くらい」とゆるく示すだけにしてある。**応募のハードルと、
記事の質のどちらを取るかでは、まず応募が来ないと始まらない。**
足りない分は採用後に依頼する。

> **下限だけでなく上限も示す理由。** 「300〜600字」とだけ書くと、
> **その量を書けない人が応募をやめる**。一方で上限が無いと、
> 1冊に数千字書かれて記事の粒度が崩れることがある。
> **目安は100〜200字・上限は目安として600字**という示し方にした。

## 質問一覧

### 1. あなたについて

| # | 質問 | 種類 | 必須 | 補足として画面に出す文 |
|---|---|---|---|---|
| 1 | お名前 | 短文 | ✅ | 記事に表示されます。**本名でなくても構いません**（ふだんお使いのお名前で結構です） |
| 2 | メールアドレス | メール | ✅ | **必須です。サイトには表示しません。**<br>掲載させていただく場合のご連絡・原稿の確認は、**すべてこのメールアドレスへお送りします。**<br>見送る場合のご連絡もこちらへお送りします |
| 3 | ご所属 | 短文 | — | 大学・研究機関・企業・書店など。**任意です** |
| 4 | 専門分野・関心のある領域 | 短文 | ✅ | 例: 経営学（組織論）／近世哲学／写真史 |
| 5 | この本を薦められる背景を、一言だけ教えてください | 長文（200字目安） | ✅ | **肩書きや形式は問いません。**「〇〇を15年読み続けている」「Xで書き続けている」「仕事で扱っている」程度で十分です。<br>うまく書けない場合は空欄でも構いません。**こちらで下書きしてご確認いただきます** |
| 6 | X（旧Twitter）のアカウント | 短文 | — | **任意です。** ご記入いただいた場合のみ、記事からリンクします。`@` は付けずにIDだけ |
| 6b | アイコン画像 | **ファイルアップロード** | — | **任意です。** 記事と選者ページに表示されます。<br>顔写真でなくても構いません（イラスト・アバターなど）。<br>**正方形に切り抜かれます**（200×200px 以上を推奨。jpg / png / webp）。<br>ご提供がない場合は、お名前の頭文字を丸く表示します |

> **6b を任意にする理由。** `README.md`「選者の顔写真」のとおり、`avatar` は
> スキーマ上も必須ではない。**研究者は写真の提供を渋る場合があり、必須にすると
> 応募のたびに交渉が発生する。** 未提供でも頭文字の丸が出るので表示は破綻しない。
>
> **「顔写真」と書かない。** 匿名で参加できるメディアなので、顔出しが条件だと
> 誤解されると応募が落ちる。求めているのは一覧での識別性であって本人確認ではない。
>
> **正方形・推奨サイズを先に伝える。** `object-fit: cover` で切り抜くため、
> 横長の写真を出すと意図しない位置で切れる。あとから差し替えを頼むより安い。
>
> **Tally の File upload 項目を使う。** 受け取った画像は
> `public/selectors/<ファイル名>` に置き、`src/data/selectors.json` の
> `avatar` にファイル名を書く。ファイル名は登録時にこちらで
> 選者ID（`yamada-taro.jpg` など）へリネームする。
> **権利の確認は確認稿の段階で行う**（ご本人に権利のある画像か）。
> フォームで先に聞くと項目が増えて離脱要因になる。

> **5 の見出しから「専門」「詳しい」を外している理由。** 記事スキーマ側の
> `credentials` は必須のまま（`README.md`「`credentials` を必須にしている理由」）だが、
> **「その領域に詳しい理由」と正面から聞くと、自分は名乗れるほどではないと
> 判断して離脱する人が出る。** とくに X 経由の応募者は肩書きを明示していないことが多い。
> 必須は外さない（外すと空のまま流れて、読者にとって唯一の手がかりが消える）が、
> **「書けなければこちらで下書きする」という逃げ道を設問文に書く。**
> 掲載前の確認稿は必須プロセスなので、承認の場は最初から確保されている。
> 詳しくは `docs/outreach.md`。
>
> **2 を必須にし、6 を任意にしている理由。** 名前が匿名でよい以上、
> **本人が原稿を見て了承した記録**が唯一の担保になる。
> 見送るときの連絡先でもあり、掲載後の訂正・削除の窓口でもある。
> **連絡手段はメールに一本化する**（Xを持たない選者を排除しないため、
> またDMは見落とし・送信制限が起きるため）。X は掲載時のリンク先にすぎない。

### 2. 選書

| # | 質問 | 種類 | 必須 | 補足 |
|---|---|---|---|---|
| 7 | 選書のテーマ（分野） | **選択（1つ）** | ✅ | 選書がいちばん近い分野をお選びください |
| 8 | 記事のテーマ | 短文 | — | 分野の中でどんな切り口かを一言で。<br>例:「行動経済学を初めて学ぶ人へ」「写真を『読む』ための5冊」 |
| 9〜 | **本 × 3冊以上**（下記の繰り返し） | | ✅ | |

**7 の選択肢は `src/data/topics.json` の大トピック（学問31件 ＋ 企画1件）をそのまま使う**
（記事の `topic` が閉じた語彙のため、自由記述だと必ずこちらで割り当て直しが要る）。

```
数学 / 物理学 / 天文学 / 地球科学 / 化学 / 生物学 /
計算機科学・計算機工学 / 工学 / 都市・建築学 / デザイン学 / 農学 /
医学 / 歯学 / 薬学 / 医学・歯学・薬学以外の健康科学 /
政治学 / 軍事学・防衛学 / 法学 / 経済学 / 経営学 / 社会学 / 教育学 /
哲学 / 宗教学 / 心理学 / 言語学・語学 / 人類学・考古学 / 歴史学 /
地理学 / 文学 / 芸術 /
あまり知られていない良書（分野が絞れない場合）   ← ★必ず最後に置く
```

> **最後の1つは分野ではなく企画のお題**（`topics.json` に追加済み）。
> 肩書きのない応募者や、ジャンルをまたいで「読んでよかった無名の本」を
> 挙げてくださる方の受け皿。`README.md`「企画のお題を立てるときの注意」が
> ✅ とする型（「絶版だが読まれるべき本」）と同じもので、
> **誰でも答えられるが、有名な本ではなく無名の本が集まる**問いになっている。
>
> **必ず選択肢の末尾に置き、「（分野が絞れない場合）」と添える。**
> 上の方や無印で置くと、本当は分野が絞れる人までここを選び、
> `/topics/` が1ページに潰れて唯一のアーカイブ軸が機能しなくなる。
> **分野が絞れる記事は分野側に置く**のが原則（`人がすすめる本` と同じ扱い）。
>
> この topic を選んだ記事でも、ジャンルは `subtopic` に残せる
> （`あまり知られていない良書` の小トピックとして31分野を入れてある）。

> **小トピックは聞かない。** 31件でも選ぶ側の負担は小さくないうえ、
> 小トピックまで正確に選んでもらう必要はない（記事化のときに
> 大トピックの下から選べば足りる）。

**1冊ごとに聞くこと:**

| 質問 | 種類 | 必須 | 補足 |
|---|---|---|---|
| 書名 | 短文 | ✅ | |
| 著者 | 短文 | ✅ | |
| この本の概要や選んだ理由 | 長文（100〜200字目安） | ✅ | どんな本かの説明でも、選んだ理由でも、その両方でも構いません。<br>**100〜200字程度**で結構です。書きたいことがあれば長くしていただいても構いませんが、**最大でも600字くらい**でお願いします |

> **出版社・ISBN は聞かない。** 書名と著者があれば
> こちらで openBD / Google Books から引ける（`npm run sync:covers`）。
> 応募者に版を特定させるより、こちらで調べて**確認稿で見てもらう**ほうが速い。
> 版が複数あって迷う場合は、確認稿の段階でご本人に確かめる。

> **Tally なら「繰り返しグループ」で3冊ぶんを既定表示にし、追加できるようにする。**
> それが難しければ、3冊ぶんを固定で並べ、「4冊目以降」を自由記述の長文1つにする。
> **上限は設けない**（記事は3冊以上・上限なし）。

### 3. いちばんよかった1冊

| # | 質問 | 種類 | 必須 | 補足 |
|---|---|---|---|---|
| 10 | 挙げていただいた中で、**いちばんよかった1冊**を選ぶとしたらどれですか | 選択（上の書名） | ✅ | **迷われた場合は、世の中的にはあまり知られていない本を選んでいただけると嬉しいです。**<br>ただし、有名な本でも構いません。まずは「いちばんよかった」でお選びください |
| 11 | その本を選んだのはなぜですか | 長文（150字目安） | ✅ | 上の理由と重なっても構いません。**「この1冊を挙げた決め手」**を書いていただけると助かります |

> **聞き方を「知られていない本」から「いちばんよかった本」に変えた理由。**
> 知名度は選者にとって答えにくい（自分の周りでは常識に見える本が、
> 世間では無名ということが起きる）。**答えやすいのは「よかったかどうか」**で、
> そのうえで無名寄りを選んでほしいと添えれば、結果として拾いたい本が集まる。
> 知名度を条件ではなく**お願い**として置くのが要点。
>
> **この2問は必須にする。** ここに答えがあると `/hidden`（知る人ぞ知る本）
> に載る。`/hidden` はこのメディアの核なので、任意にして書かれないまま
> 流れると成立しない。「挙げた中でいちばんよかった1冊」は選者が必ず
> 答えられる問いなので、必須にしても負担にはならない。
> 記事のスキーマ側も、公開する記事には `bestReason` を1冊必須にしてある。

### 4. 進め方

| # | 質問 | 種類 | 必須 | 補足 |
|---|---|---|---|---|
| 12 | 記事の書き方 | 選択 | ✅ | ・自分で書く（寄稿）※基本<br>・話を聞いてほしい（取材） |
| 13 | その他・ご要望 | 長文 | — | |

### 5. 最後に必ず出す文

チェックボックスにはしない（操作を止めない）。**読める場所に置く。**

```
・いただいたご応募は、基本的に掲載させていただく方針です。
  ただし、3冊に満たない場合や、選書のまとまりが見えない場合には
  見送らせていただくことがあります。
  気になる点があれば、見送る前にまずご相談させていただきます。
・結果は、掲載する場合も見送る場合も、ご記入いただいた
  メールアドレスへ必ずご連絡します。
・掲載させていただく場合は、公開前に必ず原稿をお送りし、
  ご本人に確認していただきます。
・読みやすさのため、体裁を整えさせていただく場合があります。
・いただいた個人情報は、この件のご連絡以外には使用しません。
```

---

## 設定

- **回答があったらメール通知**を有効にする。気づかないと「必ず連絡します」が守れない
- **回答の重複送信を許可**する（書き直したい人がいる）
- 回答をスプレッドシートに出す設定は任意。**記事化は `/admin` で行う**ので、
  回答画面を見ながら打ち込めば足りる

## 作ったあと

```
① Tally でフォームを作る
② 共有URLをコピー
③ src/config.ts の applyFormUrl に貼る
④ SITE.contactEmail も埋める（フォーム準備中の案内先）
⑤ /apply の「見送る基準」を書く
```
